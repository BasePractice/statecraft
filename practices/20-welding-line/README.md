# 20-welding-line — сквозной проект курса

Управление сварочной линией: автоматная модель, реализация на C90, учёт
покрытия переходов и экспорт модели для верификатора. Проект собирает
вместе четыре лекции и служит образцом курсовой работы.

| Лекция | Что из неё здесь |
|---|---|
| 3 | модель задана таблицей переходов — её можно синтезировать практикой `03-synthesis` |
| 7 | реализация таблицей переходов с действиями, ввод-вывод отделён от логики |
| 8 | выдержки и таймауты как часть модели, а не `sleep` в коде |
| 9 | учёт покрытия переходов, экспорт модели на Promela для SPIN |

## Задача

По конвейеру приходит изделие; датчик сообщает о нём. Изделие фиксируется
зажимом, сварочная головка позиционируется к очередной точке и варит её с
выдержкой. Точек несколько; когда сварены все, зажим отпускается и изделие
уходит. Любая операция ограничена по времени: если концевик не сработал за
отведённое число тактов, линия уходит в аварию и ждёт сброса оператором.
Оператор может остановить линию из любого рабочего состояния.

## Запуск

```bash
20-welding-line                             # встроенный сценарий
20-welding-line --scenario scenario/fault.txt
20-welding-line --dot | dot -Tpng > line.png
20-welding-line --promela > welding.pml
```

Прогон печатает трассу переходов, состояние приводов и в конце — покрытие
переходов:

```
Изделий обработано: 1, аварий: 1, состояние: STOPPED
Покрытие переходов: 9 из 16
Не сработали:
  CLAMP --STOP--> STOPPED
  POSITION --TICK--> FAULT
  ...
```

## Чем этот проект отличается от остальных

**Ввода-вывода в автомате нет.** Датчики и приводы — функции в структуре
`WeldingHal`, которые подставляет вызывающая сторона: на стенде их
реализует драйвер, в тестах — эмулятор. Логика управления не знает, откуда
берутся события, и поэтому проверяется без железа.

**Граф автомата присутствует в программе явно.** Таблица `TRANSITIONS` —
это рёбра графа; по ней печатается диаграмма, считается покрытие и
порождается модель для SPIN. Во вложенных `switch`/`if` (см.
`07-simple-program`) граф существует только в голове автора.

**Одна развилка сознательно вынесена из таблицы.** После сварки точки
автомат идёт либо к следующей точке, либо на освобождение изделия — выбор
зависит от счётчика точек, то есть от данных, а не от управления. В таблице
её нет, в диаграмме она нарисована пунктиром, в модели Promela —
недетерминированной альтернативой. Это типичная граница между управлением
и данными, и её стоит проводить осознанно.

**Покрытие переходов набирается набором прогонов, а не одним.** Остановка
оператором заканчивает работу, поэтому каждый переход в `STOPPED` требует
своего прогона; тесты объединяют покрытие через `welding_merge_coverage` и
требуют 100 %. Разница между покрытием состояний и покрытием переходов
видна прямо в тестах: короткий сценарий посещает все состояния, кроме
`STOPPED`, но покрывает едва половину переходов.

## Проверка модели

```bash
20-welding-line --promela > welding.pml
spin -a welding.pml && gcc -o pan pan.c && ./pan -a
```

Модель абстрагируется до графа переходов: события выбираются
недетерминированно, выдержки и счётчик точек не моделируются. Проверяются
свойства управления — например, что после аварии линия обязана вернуться в
рабочий режим или остановиться:

```promela
ltl recovery { [] (state == FAULT -> <> (state == IDLE || state == STOPPED)) }
```

## Что доделать студенту

Проект намеренно оставлен неполным в трёх местах — это и есть задания
курсовой работы:

1. **Ручной режим.** Добавить состояние наладки, в котором оператор
   двигает головку по одной точке. Проверить, что покрытие переходов
   осталось полным, и объяснить, сколько новых тестов понадобилось.
2. **Второй пост сварки.** Две головки работают параллельно над разными
   точками одного изделия. Это ортогональные регионы из лекции 8: описать
   их двумя автоматами и объяснить, что произойдёт с числом состояний,
   если свести их в один плоский автомат.
3. **Проверка свойства безопасности.** Сейчас утверждение «горелка не
   включается, пока изделие не зажато» проверяется тестом на одном
   сценарии. Сформулировать его как свойство LTL и проверить на модели с
   данными — либо объяснить, почему абстракция до графа переходов этого
   свойства не выражает.
