# 07-three-ways — один автомат тремя способами

Практика к лекции 7. Управляющий автомат шлагбаума реализован трижды:

| Файл | Способ | Где хранится модель |
|---|---|---|
| `barrier_switch.c` | вложенный `switch` | в потоке управления |
| `barrier_table.c` | таблица переходов | в данных: массив 4 × 5 |
| `barrier_state.c` | паттерн State (GoF) | в объектах-состояниях |

Все три работают с одним внешним миром: действия не идут в железо, а
пишутся в трассу (`struct BarrierTrace`). Тесты сравнивают трассы трёх
реализаций буква в букву — если реализации разошлись, значит какая-то из них
описывает уже другой автомат.

## Автомат

Шлагбаум на въезде: четыре состояния, пять событий.

```
состояние    card       opened    passed     closed     tick
CLOSED       OPENING    —         —          —          —
OPENING      —          OPEN      —          —          —
OPEN         —          —         CLOSING    —          CLOSING по выдержке
CLOSING      OPENING    —         —          CLOSED     —
```

Прочерк — событие игнорируется: автомат остаётся в том же состоянии и не
выполняет действий. Игнорирование задано в таблице явно, пустых клеток нет.

Два места, ради которых пример и выбран:

- **реверс**: `CLOSING` по `card` — машина подъехала, пока створка опускалась,
  и шлагбаум обязан пойти вверх, а не «доопуститься сначала»;
- **сторожевое условие**: `OPEN` по `tick` ведёт в `CLOSING` только когда
  счётчик выдержки дошёл до `BARRIER_OPEN_TIMEOUT`. Счётчик — расширенное
  состояние, в чистой таблице переходов его не выразить.

## Запуск

```bash
07-three-ways                          # сценарий по умолчанию, три трассы
07-three-ways card opened passed closed  # свой сценарий
07-three-ways --coverage               # покрытие переходов набором сценариев
```

Вывод `--coverage` показывает, что ни один отдельный сценарий не даёт больше
35 % покрытия переходов, а весь набор из шести — ровно 100 %.

## Что здесь сравнивать

Три реализации отличаются не результатом, а ценой изменений:

- добавить состояние: в `switch` — новая ветка плюс правки в остальных ветках;
  в таблице — новая строка; в State — новый объект, остальные не трогаются;
- добавить событие: в `switch` — правка каждого состояния; в таблице — новый
  столбец (компилятор не напомнит его заполнить, зато незаполненная клетка
  видна глазами); в State — правка каждого обработчика;
- посчитать покрытие переходов: в таблице — счётчик на клетку, пять строк
  кода; в двух других реализациях нужен инструментарий покрытия по строкам, и
  соответствие «строка ↔ переход» приходится восстанавливать вручную.

Разбор с числами — в лекции 7, § «Три реализации одного автомата».
